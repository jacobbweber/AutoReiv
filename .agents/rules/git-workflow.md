# Rule: Git Workflow, Conventional Commits, & Semantic Versioning

---

## 1. Branching Strategy & Staging Environments

To ensure the Human Visionary and QA Tester can safely verify features before production releases, all work follows a structured branching model:

```text
[main: Production (Tagged vX.Y.Z)]
   ▲
   │ (Release PR after Human QA Approval)
[qa: Integration & Human Testing Sandbox]
   ▲
   │ (Feature PR with Human QA Runbook)
[feat/<slug> or fix/<issue-id>-<slug>]
```

1. **`main` (Production Branch)**:
   - Contains production-ready, release-tagged code (`v1.0.0`, `v1.1.0`).
   - Merges into `main` occur exclusively from `qa` via release PRs.
2. **`qa` (Integration & Human QA Branch)**:
   - The integration branch where features land for testing.
   - All feature and fix branches must target `qa` in their Pull Requests.
3. **Working Branches (`feat/*`, `fix/*`, `chore/*`)**:
   - Cut from `qa`.
   - Branch naming conventions:
     - Features: `feat/<feature-slug>` (e.g., `feat/magic-link-auth`)
     - Bug fixes: `fix/<issue-id>-<slug>` (e.g., `fix/104-token-expiry`)
     - Maintenance: `chore/<slug>` (e.g., `chore/upgrade-deps`)

### 1.1 Branch Lifecycle & Stale Branch Pruning

To maintain a clean repository and eliminate dead branch drift:

1. **Creation**: Cut an isolated `feat/<slug>` or `fix/<slug>` branch from the latest `qa`.
2. **Execution**: Implement changes following test-locked delivery.
3. **Verification**: Run pre-flight DoD gates (`npm run preflight`).
4. **Merge**: Switch to `qa` and merge the working branch (`git checkout qa && git merge <branch>`).
5. **Immediate Pruning**: **Immediately delete the local working branch** via `git branch -d <branch>`. Merged feature branches must NEVER linger in the local workspace.

## 2. Conventional Commits Standard

All commit messages generated by AI agents must strictly follow the **Conventional Commits 1.0.0** format:

```text
<type>(<scope>): <imperative description>

[optional body with rationale and CARD-xxx references]

[optional footer(s) for BREAKING CHANGE or Closes #123]
```

### Commit Types & SemVer Mapping

| Type                        | Description                                             | SemVer Impact        |
| :-------------------------- | :------------------------------------------------------ | :------------------- |
| **`feat`**                  | A new feature or capability                             | **MINOR** (`v1.1.0`) |
| **`fix`**                   | A bug fix                                               | **PATCH** (`v1.0.1`) |
| **`refactor`**              | Code change that neither fixes a bug nor adds a feature | None / Patch         |
| **`test`**                  | Adding or correcting tests                              | None                 |
| **`docs`**                  | Documentation or specification updates                  | None                 |
| **`perf`**                  | Code change that improves performance                   | **PATCH**            |
| **`chore`**                 | Build tasks, package configs, or governance updates     | None                 |
| **`!` / `BREAKING CHANGE`** | Breaking change to public API or data model             | **MAJOR** (`v2.0.0`) |

### Atomic Commit Cadence

Commit atomically per logical vertical slice or refactor:

1. `feat(auth): implement token generator [CARD-123]`
2. `test(auth): add token expiry regression tests`
3. `refactor(auth): prune legacy authentication helpers`

## 3. Semantic Versioning & CHANGELOG Maintenance

This repository adheres to **Semantic Versioning 2.0.0** (`MAJOR.MINOR.PATCH`):

- Increment **MAJOR** when making incompatible API / schema changes.
- Increment **MINOR** when adding backwards-compatible functionality (`feat`).
- Increment **PATCH** when making backwards-compatible bug fixes (`fix`).

### `CHANGELOG.md` Invariants

Before opening any PR, update `CHANGELOG.md` under the `## [Unreleased]` section following the _Keep a Changelog_ standard:

- `### Added`: for new features (`feat`).
- `### Changed`: for changes in existing functionality.
- `### Deprecated`: for soon-to-be-removed features.
- `### Removed`: for now-removed features.
- `### Fixed`: for any bug fixes (`fix`).
- `### Security`: in case of vulnerabilities.

## 4. 3-Tier Task Management & Execution

1. **Macro Tier (Milestones & Roadmap)**:
   - High-level business intent, epics, and milestones tracked in `steering/roadmap.md`.
2. **Meso Tier (Card Checklist in `docs/cards/CARD-xxx.md`)**:
   - Work card acceptance criteria and task breakdown.
   - Committed to git as the permanent, team-visible contract of what was built.
3. **Micro Tier (In-Session Plan)**:
   - Ephemeral, live execution scratchpad (`implementation_plan.md`) scoped to the active card during the session.
